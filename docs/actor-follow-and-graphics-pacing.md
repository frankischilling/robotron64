# Actor following and graphics pacing

Three complete routines replace executable ROM fallback bytes. Their addresses remain temporary names because no original symbols survive for these functions.

| Function | Source | Complete instruction bytes |
| --- | --- | ---: |
| `func_80029020` | `src/game/actor_position_follow.c` | 144 |
| `func_80035360` | `src/game/actor_value_follow.c` | 324 |
| `func_8004FEA8` | `src/boot/graphics_setup.c` | 476 |

`func_80029020` visits the twenty entries in the existing `D_800A4580` actor pair table. When a follower exists, it copies the source actor's three position words and submits that position through `func_800290B0`. The table already has a source-owned BSS definition; this routine adds no storage.

`func_80035360` follows the primary actor at owner offset `0x08`, copies its position, applies the existing actor relationship helper, and sets an object angle from the frame clock multiplied by twenty. It divides the primary actor's first value word by 256, caps values at three, then subtracts that index from three. When a nonzero index differs from the resource's actor-kind field, it sets state byte `0x21` to two and creates the secondary actor through the corresponding `D_8009AFD8` entry. The resulting actor pointer lives at owner offset `0x0C`; a successful allocation receives the same owner pointer. These offset names describe observed access, not a confirmed gameplay role. Reusing the second parameter for the computed value preserves IDO's stack homes and matches the whole routine.

`func_8004FEA8` initializes the graphics message queue and scheduler client, then waits for messages indefinitely. Message one consults `D_8008D574`: state zero increments `D_8008D578` while its unsigned value is below two; state one increments only a zero counter. States two, three, five, and thirty have explicit empty cases. Message two decrements the counter. Message three calls `func_80064CE0(1.0f)` and adds two. The unsigned state bound, signed `-1` exception, and explicit empty cases are retained from the target control flow.

The graphics routine must compile in the same translation unit as its two preceding setup helpers. Its nested switch emits a 31-entry dispatch table at `0x80095BF0` (ROM `0x967F0`), occupying 124 bytes. The build owns that compiler-generated table and verifies every entry after relocation. No table bytes are copied from the baserom into source. The precise original selection of empty labels is not uniquely recoverable from their shared branch destinations; this source preserves the observed behavior, bounds, and complete table.

All three use the established game profile: IDO 5.3, `-O2 -G 0 -non_shared -mips1 -32`. Independent comparisons cover complete procedure spans, and graphics comparison covers the complete 628-byte setup object. Current validation is generated by `make verify`, the runtime comparisons, and `make progress`; the accompanying provenance ledger records the verified checkpoint. The whole-ROM comparison includes remaining fallbacks and does not imply that the source decompilation is complete.
